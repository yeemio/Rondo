# MVP activity v1 extension

This candidate adds the registered `rondo.activity@1` renderer and `mvp.activity.v1` task family. It preserves the 12 prior releases, the existing `rondo.v1` command envelope, Host authorization, command receipt transaction, attempt/cycle lifecycle and SQLite schemaVersion 1. No legacy database migration or second learning store is introduced. The three activities use the same `createLearningServer` as the prior content.

- Public activity state: activity kind, ratio scale, inspected authored card IDs and the learner's draft. Operations are a closed union, task-checked server-side. Draft saves are permitted in any active phase and never rewrite submitted answers, first prediction or explanation revisions. `BOARD_SVG` and `BOARD_TABLE` name the object/table expressions; all critical actions use keyboard-accessible DOM buttons and inputs, with no WebGL dependency.
- Public response extension `codeRun`: logical job ID plus exact source/stdin snapshots. `code.requestRun` adds stdin and requires a question/release/renderer binding and current attempt version. Source and input byte limits are checked by the learning service and accepted b2 worker. Requests are durable event facts admitted in the normal receipt transaction; only after commit may execution start. Retrying a committed request returns its original job. A changed payload under the same key conflicts.
- `code.runStatus` projects the public source/input/compiler/image/instance/worker job/request identities and visible output/diagnostics. Private checks and their verdicts stay in server events, and only the normal submission creates the learning evaluation. The visible worker job ID always refers to the visible stdin. Private worker receipts are retained separately in server-only event fields. Cancellation waits for the accepted worker's confirmed terminal state. Nonterminal jobs from an earlier Host instance read as UNKNOWN; they are never automatically re-executed on reboot.
- `learning.activityHistory` exposes only the authenticated learner's MVP attempts, or the guardian's selected family learner. It includes immutable predictions, all submissions/evaluations, all explanation revisions and accurate code runs. Reference explanation/program are revealed only at REVIEW after the learner has saved an explanation. A new attempt preserves all older attempts and links to the previous terminal attempt.
- Private rule `MVP_ACTIVITY_TRUTH_V1` is a data-only, strictly parsed registered rule family. Runtime/infrastructure failures are UNSCORABLE, with an explicit retry path. Compilation or visible sample success is never itself task correctness.

Scope index in `modules/curriculum/mvp.ts` is public metadata. Build generates three immutable content releases from this source and server rule data; the web build never bundles private truth. Existing 12 content releases are still loaded. No online model or real learner data is used.

## R2: approved statement prediction carrier

`activity.statement.v1` is an additional strict prediction member for the three registered MVP activities. It carries `activityId` plus the exact nonblank statement (at most 2000 characters and 6000 UTF-8 bytes). The server matches activityId against current question/task/release and the registered activity family. Unknown carrier versions and activities reject. The original geometric claims member and its empty-claims-unless-uncertain rule are unchanged. `uncertain` is an explicit learner choice; confident statements stay false. Draft uncertainty is optional for old saved states and explicitly persisted by the new UI. This uses the same immutable first prediction, receipt/idempotency and history; it never creates an evaluation or mastery claim.

The r2 form invokes `submitActivityPrediction` from `apps/web/src/studio/prediction.ts`; verification executes this same callback with real SQLite/domain calls, capturing its exact payloads for all three activities. Browser interaction remains a separate controller check.
